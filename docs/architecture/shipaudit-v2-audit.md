# ShipAudit V2 — تدقيق المنتج وخريطة إعادة التأسيس

> تعريفات المركز المالي المعتمدة موثقة في [financial-position-contract.md](./financial-position-contract.md). يجب عدم استخدام Accounting Outstanding وOperational Collectible كمترادفين.

التاريخ: 2026-08-28
الحالة: مرجع تنفيذي حيّ؛ يحدّث مع انتقال كل مساحة عمل إلى V2.

## الخلاصة التنفيذية

ShipAudit ليس نظام محاسبة أو CRM جديدًا. هو طبقة تشغيل وقرار فوق Zoho Books، ومنصة لمحة، وHatif/WhatsApp/IVR، وملفات الناقلين والبنوك. المحرك التشغيلي متقدم ويحتوي بالفعل على Customer/Store 360، تحصيل، حملات، دورة محاسبية، تدقيق ناقلين، ومراقبة مصادر. المشكلة الأساسية في V1 هي أن خبرة المنتج تطورت أسرع من الغلاف وهندسة المعلومات: مسارات كثيرة، طبقات CSS متراكمة، وصفحات تاريخية بقيت مساوية لمساحات العمل الحديثة في الوصول المرئي.

قرار V2 هو المحافظة على محرك البيانات والتكاملات، وتوحيد الوصول حول: إشارة ← نتائج ← كيان ← سياق ← إجراء ← نتيجة موثقة.

## Architecture الحالية

- الواجهة: React 18 + Vite 5 + `react-router-dom`.
- الغلاف والصلاحيات والمسارات: `src/App.jsx`؛ الملف يجمع route guards وlazy pages وPageSlot keep-alive.
- قاعدة البيانات والتكامل الخلفي: Supabase/Postgres + Edge Functions + RPCs.
- مصدر هندسة المعلومات الظاهرة: `src/lib/navigation.js` عبر `NAV_SECTIONS` و`NAV_ITEM_IA`.
- الوصول للبيانات: طبقة خدمات في `src/lib/*Service.js`، مع بعض الجلب المتبقي داخل الصفحات.
- النمط: CSS عالمي متعدد الطبقات؛ أحدث طبقة تأسيسية هي `src/shipaudit-os-v2.css`، لكن ملفات أقدم لا تزال تشارك في الـcascade.
- الحالة: React local state وURL state؛ لا يوجد store مركزي يحتاج استبدالًا.

## تعريفات مالية لا يجوز دمجها

- `outstanding`/المستحق: مجموع الفواتير المفتوحة المرتبطة وفق قراءة Zoho/خدمة التحصيل.
- `overdue`/المتأخر: جزء المستحق الذي تجاوز تاريخ الاستحقاق؛ لا يساوي كامل الرصيد.
- شرائح الحملات: فواتير متأخرة فقط `1–15`, `16–30`, `31–60`, `61–90`, `+90`؛ استحقاق اليوم لا يدخل `1–15`.
- الرصيد الافتتاحي: شريحة مستقلة ولا يدمج تلقائيًا مع `+90`.
- `unused credit`: رصيد دفعة/إشعار غير مستخدم في Zoho، وليس محفظة لمحة.
- `wallet balance`: رصيد منصة لمحة، وليس رصيد Zoho أو صافي المستحق.
- COD المستلم: تدفق نقدي وليس إيرادًا.
- تكلفة الناقل: لا تعتمد من Excel الخام؛ مصدرها مراجعة معتمدة وموثقة عقديًا.

## أهم الكيانات

- لا حذف في هذه المرحلة؛ الإخفاء من الوصول الرئيسي يسبق التنظيف.

## مشاكل IA/UX المثبتة

1. `App.jsx` يجمع صلاحيات ومسارات وغلافًا وصفحات كثيرة؛ تغيير IA عالي الاحتكاك.
2. الغلاف كان يحتفظ بتعريف CSS لشريط رئيسي دون JSX فعلي، ثم طبقة CSS أخيرة تلغي الشبكة بالكامل.
3. Navigation Hub يعرض كتالوج وجهات؛ مفيد كدرج جوال، لكنه ليس تنقل حاسب دائمًا.
4. صفحة الدخول كانت تصف النظام كتدقيق شحن/COD/Webhook فقط، وهو وصف قديم للمنتج.
5. مركز القيادة الحالي قريب من الهدف لكنه كان يعرض الاستثناءات كبطاقات منفصلة، مع بحث مكرر داخل الصفحة فوق البحث العام.
6. بعض أخطاء المصدر تظهر `error.message` مباشرة؛ يجب إبقاء الملخص الإداري أولًا والتفاصيل التقنية ثانوية.
7. بعض الصفحات التاريخية ما زالت تستخدم Cards وinline styles بكثافة رغم وجود workspaces حديثة.
8. Global Search يغطي الصفحات، الناقلين، المتاجر، فواتير Zoho وAWB؛ لا يغطي بعد دفعات العملاء أو العمليات البنكية.

## تدقيق CSS وResponsive

- قرابة 18 ألف سطر CSS عالمي.
- `workspace-layout.css` وحده يقارب 8 آلاف سطر.
- نحو 2300 استخدام `!important` و1249 قيمة لون hex و123 media query في الفحص الأولي.
- ملفات متعددة تعيد تعريف `.app-layout`, `.sidebar`, `.topbar`, `.login-*`؛ ترتيب الاستيراد أصبح جزءًا من السلوك.
- توجد tokens جيدة في `shipaudit-os-v2.css`، لكن الطبقات القديمة ما زالت تتجاوزها.
- إصلاح V2 يكون بمكونات ذات نطاق واضح وطبقة نهائية صغيرة، ثم إزالة القواعد المثبت أنها غير مستخدمة؛ لا يضاف theme ثالث عام.
- الجوال يملك أساسًا جيدًا: PageSlot flow، safe-area spacer، واستراتيجيات جدول متعددة، لكنه يحتاج QA لكل workflow لا مجرد media queries.

## IA المعتمدة لـV2

المراكز المرئية ثابتة في سبعة مداخل فقط:

1. الرئيسية — مركز القيادة والقرارات.
2. العملاء — البحث وStore 360.
3. المبيعات — النمو والفرص والحملات والاتصال.
4. المالية — تحصيل العملاء، النقد، Zoho، المطابقة، الربحية والإقفال.

Desktop يستخدم شريطًا تنفيذيًا مضغوطًا لهذه المراكز فقط. صفحات المركز تظهر كـViews/اختيار عرض داخل مساحة العمل. Mobile يستخدم درجًا واحدًا، ولا يعيد الشريط المكتبي ولا ينشئ قائمة سياقية ثانية.

## ترتيب التنفيذ

- Slice 1: تأسيس الغلاف، التنقل، هوية الدخول، وإزالة البحث المكرر من الرئيسية.
- Slice 2: تحويل Command Center إلى قائمة قرارات/نتائج مع provenance وdrill-down.
- Slice 3: تثبيت Customer 360 كمسار الكيان الوحيد وتحسين حالات المصدر والخطأ والإجراء.
- Slice 4: توحيد Financial Workspace وResult Sets وBulk Action contract.
- Slice 5: ربط Campaign Workspace بجماهير التحصيل/المبيعات ونتائج القنوات.
- Slice 6: ترحيل بقية التشغيل والتقارير والإدارة، ثم تنظيف CSS/legacy المثبت.
- QA بعد كل slice: build، عقود الاختبار، المتصفح، console، RTL، 375/390/430/768/1024/1280/1440+.

## مخاطر لا يجوز كسرها

- مطابقة العميل/المتجر بواسطة Store ID واللقطة، لا الاسم أو الهاتف فقط.
- قواعد Aging وافتتاحي الحساب وتعريف المستحق القابل للتحصيل.
- حدود وصلاحيات Lamha status، وفحص الحالة بعد الكتابة، وسياق `financial_policy`.
- حماية جمهور الحملات وكون فتح المراجعة لا يطلق الإرسال.
- عدم إنشاء أو رفع bank statement إلى Zoho.
- الإثبات العقدي للمراجعات وجدولة الناقلين وإسناد `scheduleSlot`.
- اكتمال الدورة من البيانات الفعلية وفشل المصدر كحاجز صريح.
- route guards والصلاحيات الدقيقة، مع عدم اعتبار المدير دليل جاهزية الفريق.
