# نموذج تشغيل الأتمتة — ShipAudit V2

آخر تحديث: 2026-09-04

## العقد الموحد

كل وكيل في ShipAudit يمر بالتسلسل نفسه:

`Source → Trigger → Conditions → Audience → Action → Safeguards → Result → Audit`

وجود Trigger أو Preview لا يعني أن Action نُفذ. صلاحية التنفيذ تأتي من المشغّل الفعلي، وصلاحية المستخدم، ومستوى المخاطر، وسياسة الاعتماد معًا.

## أنواع المستلمين

- `customer`: عميل أو متجر؛ الهوية الأساسية للتواصل هي رقم الجوال السعودي المطبّع.
- `employee`: موظف محدد بإسناد موثق أو استراتيجية توزيع معلنة. لا يُختار موظف افتراضيًا.
- `management`: تقرير أو تنبيه داخلي للإدارة.
- `internal_queue`: قائمة عمل أو مراجعة داخل ShipAudit دون إرسال خارجي.

## أنواع الإجراءات

- `send_hatif_template`: إرسال قالب معتمد للعميل عبر هاتف.
- `notify_employee_template`: إرسال قالب موظفين معتمد إلى الموظف المسؤول.
- `create_task`: إنشاء مهمة داخلية؛ يحتاج عقد إسناد ومنع تكرار مستقلين.
- `review_queue`: بناء قائمة قرار داخل النظام، بلا تنفيذ خارجي.
- `in_app_report`: حفظ تقرير داخل النظام.
- `linked_system_agent`: تمثيل وكيل نظام قائم له مشغله وسجله المستقلان.
- `account_action`: تغيير حالة حساب؛ إجراء حرج لا يعمل تلقائيًا.

## مستويات المخاطر والاعتماد

- منخفض: قراءة، مراقبة، تقرير داخلي.
- متوسط: تواصل غير مالي أو تنبيه موظف.
- مرتفع: تواصل تحصيل أو إجراء قد يؤثر على تجربة العميل.
- حرج: إيقاف/تشغيل حساب أو كتابة مالية. يمنع `automatic` ويحتاج اعتمادًا صريحًا لكل تشغيل مع فحص حي.

سياسات الاعتماد: `none`، `operator_review`، `manager_approval`، `explicit_each_run`.

## حواجز عامة

1. لا يعمل وكيل يعتمد مصدرًا خارجيًا على لقطة جزئية أو قديمة.
2. قوالب هاتف التلقائية تحتاج عقدًا معتمدًا يثبت عدد المتغيرات وترتيبها ومصدرها.
3. يمنع تعارض التواصل الآلي مع أي رسالة أخرى للجوال خلال 24 ساعة.
4. يمنع تكرار الجوال ضمن الدفعة، مع الاستثناء المقصود لترحيب متجر جديد في لقطة لاحقة.
5. الحالة `inactive` وحدها تعني أن حساب لمحة موقوف؛ `active` و`idle` و`stopped` حسابات تعمل.
6. تغيير حالة الحساب يتطلب فحص Lamha حيًا، ولا يعتمد المرآة اليومية وحدها.
7. كل تشغيل يثبت نسخة القاعدة، لقطة المصادر، المؤهلين، المستبعدين، المراجعة، النجاح، الفشل، والحالة المجهولة.
8. لا تعاد الحالة المجهولة تلقائيًا؛ إعادة المحاولة للفشل المؤكد فقط.

## العقد المالي

- `Accounting Outstanding`: الرصيد المحاسبي الخام من Zoho.
- `Operational Collectible`: فواتير قابلة للتحصيل تشغيليًا حسب قواعد النظام الحالية، ومنها استبعاد الرصيد `<= 0.50`.
- `Residual Balance = Accounting Outstanding - Operational Collectible` دون tolerance.
- التحصيل، الحملات، ومراجعة الإيقاف تستخدم `Operational Collectible`، ولا تعتبر `Residual Balance` دينًا تشغيليًا.
- الرصيد الافتتاحي مستبعد من الأتمتة المالية حتى اعتماد قرار أعمال منفصل.

## فجوتان تمنعان تفعيل تنبيهات الموظفين

1. لا يوجد عقد قالب هاتف خاص بالموظفين يحدد متغيراته، مختلف بوضوح عن قوالب العملاء.
2. لا يوجد في دليل متجر لمحة مالك مبيعات/حفاظ موثق يمكن الاعتماد عليه. يجب اعتماد مصدر الإسناد أو سياسة توزيع معلنة قبل الإرسال.

لا يُعالج هذان النقصان باختيار موظف عشوائي أو إعادة استخدام قالب عميل؛ تبقى القواعد مسودة حتى اكتمال العقدين.
